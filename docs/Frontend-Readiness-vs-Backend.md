# LocalBuddy — Front-end Readiness vs Backend
*The real Angular app (`localbuddy-frontend`) audited feature-by-feature against the 192 backend capabilities · July 2026*

## Headline

**≈ 72% of the backend's feature surface is delivered in the Angular front-end.** Of **191** backend features: **118 implemented**, **39 partial**, **34 missing**. (For contrast, the static `landing/` prototype covered ~5%.)

Readiness metric: implemented = 100%, partial = 50%, missing = 0%, averaged across features.

## ⚠️ Weakest — and it's the revenue path: Availability, bookings & pricing (50%)

The traveller-facing happy path is solid: guests and logged-in users can browse real availability slots, pick date/time/party, choose shared vs private-buyout, apply promo/referral codes, and check out via Stripe (src/app/features/booking/checkout.component.ts + core/services/booking.http.ts). Hosts have a working slot calendar (create/block/unblock/delete) in host-dashboard.component.ts. Admin has real rate & refund-policy management (rates.service.ts, admin-config.service.ts) plus booking cancel/reschedule (admin-bookings.service.ts).

But large parts of the backend cluster have NO wired UI, concentrated in two areas: (1) Booking lifecycle — the host operational console is stubbed out: HttpHostService.getHostBookings returns of([]) and markBookingCompleted throws 501, so there is NO host accept/decline, host cancel, or completion/safety-gate flow. The domain BookingStatus is collapsed to just confirmed|completed|cancelled (core/models/index.ts line 197; mapper mapApiBookingStatus lines 485-489), erasing 8 of the 11 backend states. (2) Pricing transparency — the breakdown shown to users (checkout.component.html lines 170-186) is a frontend-computed perPerson×guests + a flat 10% SERVICE_FEE_RATE (booking.service.ts line 5). It shows NO VAT, no host-commission split, no cost-bearer/absorption, and no backend settlement breakdown; those exist only as admin rate-config screens, not on any booking.

Two correctness gaps worth flagging: age-band composition is collected in the checkout UI (adults/teens/children/infants) but BookingDraft (core/models/index.ts) has no band fields and booking.http.ts always sends adults: draft.guests with teens/children dropped — so weighted per-band pricing never reaches the API despite the DTO (CreateBookingRequest) supporting it. And the per-slot privateBookingAvailable flag from the availability DTO is ignored; the private toggle is gated only by experience.bookingMode, not by whether the specific slot is still buyout-eligible. Admin manual/offline booking creation is entirely absent (admin-bookings.service.ts has list/get/cancel/reschedule only). Scheduled/backend-internal features (seat-lock concurrency, pending-payment expiry sweep, guaranteed-departure job, reliability summaries) have no frontend surface, as expected.

## Per-cluster detail

### 1. Accounts, identity, consent & data rights — 74%

The identity/account/GDPR/consent cluster is the best-wired part of the app: nearly every backend endpoint has a real Angular service (auth.gateway.ts, consent.service.ts, gdpr.service.ts, admin-users.service.ts, admin-gdpr.service.ts) with JWT-bearer auth (token-store.ts + http.interceptors.ts) and route guards (auth.guard.ts, role.guard.ts). Real UI exists for login/register, profile view+edit (account.component), admin user directory + suspend/activate (admin.component users tab), admin GDPR deletion-request processing (moderation>gdpr subtab), and self-service GDPR export + deletion request (account Privacy & data section). Most significant GAPS: (1) Social login is dead in the browser — the Google button calls loginWithGoogle() which unconditionally throws 501 'not available yet' (auth.gateway.ts:81); the working social() method that POSTs /auth/social is never invoked, and no Facebook/Apple UI exists. (2) Sign-up password validator is only minLength(6) (auth-form.component.ts:279) versus backend's 8-100 + upper/lower/digit/special rule, and the register form has NO role picker so travelers vs hosts cannot pick a role at sign-up (RegisterInput.role is left undefined). (3) Verification flags + rating fields (emailVerified/phoneVerified/ratingAvg/totalReviews) are dropped by mapUserResponse (mappers.ts:67) and never shown in any UI. (4) Consent is enforced silently (ensureTraveler/LocalConsents before booking/hosting) but there is NO versioned-consent UI: the current version string is never displayed and the checkout 'agree to terms' checkbox is a plain client-side checkbox, not tied to the /consents version. (5) Self-service profile edit only sends fullName to /account/me (auth.gateway.ts updateProfile), so phone editing is not wired despite backend support. (6) Admin user creation and the users' own deletion-request history listing (myDeletionRequests) have services/models but no UI. (7) Audit logging correctly has no dedicated UI, matching the backend (empty placeholder), so it is treated as N/A-implemented via the consent/deletion trail already surfaced in admin.

**Gaps (partial ◐ / missing ✗):**

- ◐ **Email & password sign-up** — features/auth/auth-form.component.ts (register mode) + core/services/auth.gateway.ts:register() POSTs /auth/signup then chains login; BUT password validator is only minLength(6) (line ~279, not backend's 8-100+complexity) and there is no role picker in the register form so RegisterInput.role is left undefined
- ◐ **Social login (Google, Facebook, Apple)** — Google button in auth-form.component.ts (google() -> auth.loginWithGoogle()) but auth.gateway.ts:81 loginWithGoogle() unconditionally errors ApiError('Social sign-in is not available yet',501); working social() POST /api/auth/social exists (gateway line 89) but is never called; no Facebook/Apple UI
- ◐ **Self-service profile editing** — account.component.ts saveProfile() (line 396) -> auth.updateProfile -> auth.gateway.ts PUT /account/me, but body only sends { fullName } (AccountUpdateRequest); phone is NOT sent despite backend allowing phone edit; UI edits name/languages/avatar only
- ✗ **Verification flags & rating fields** — core/api/mappers.ts:67 mapUserResponse drops emailVerified/phoneVerified/ratingAvg/totalReviews from UserResponse; no account or admin template surfaces verified badges or rating/review counts for the user record
- ✗ **Admin user creation** — No createUser/POST /users call in features/admin (grep found only trustSvc.createRestriction); AdminUsersService exposes only list() + setStatus(), no create method, no create-user UI
- ◐ **Versioned consent acceptance** — core/services/consent.service.ts POSTs /consents/accept-required-traveler|local and reads currentVersion; called silently via ensureTravelerConsents() in checkout.component.ts:418 and ensureLocalConsents() in host-experience-form.component.ts:419; but no UI ever displays the version or the specific consent documents — checkout.component.html:111 is a plain client-side 'agree' checkbox not tied to the versioned consent record
- ◐ **Consent status check & enforcement gate** — consent.service.ts myStatus() GET /consents/my-status with missingTraveler/missingLocal is used only internally by ensureTraveler/LocalConsents() to auto-accept before booking/hosting; there is no UI prompt listing outstanding/missing consents to the user
- ◐ **Account deletion / anonymisation request** — gdpr.service.ts requestDeletion() POST /account/gdpr/delete-requests wired to account.component.ts requestDeletion() (line 184) with confirm() + button (account.component.html:239); but myDeletionRequests() GET listing exists in the service and is NOT surfaced — users cannot view their past requests

### 2. Hosts, cities, categories, experiences & media — 93%

Display works, one endpoint unused

### 4. Payments, payouts, invoicing & growth money — 74%

Broad, real coverage: dedicated HTTP services exist for payments, host payouts/Connect, invoices, gift cards, promo codes, referrals, deals, and admin finance/rates, each wired to real UI (checkout, account, host-dashboard payouts tab, gift-cards page, deals page, and a large admin console). Strongest: Stripe checkout, host earnings/payouts, invoicing/receipts, and admin deals are essentially complete. Weakest that pull the score down: pricing/VAT engine surfacing and promo/voucher richness. Key gaps: (1) Checkout computes the breakdown client-side with a hard-coded flat SERVICE_FEE_RATE=0.1 in booking.service.ts and never surfaces the backend's real breakdown (VAT per leg, commission, place-of-supply, host payout). (2) Gift-card redemption is only offered POST-booking on confirmation.component.ts, not applied at checkout to reduce the Stripe charge as the backend supports. (3) Targeted vouchers / cost-bearer (HOST/PLATFORM/SPLIT) / combinable flag and multi-code stacking are absent; admin promo form (CreatePromoCodeRequest) and checkout both handle only a single simple code. (4) Refund amounts/status and host clawback are not surfaced in guest or host UI, though admin cancellation-refund policy CRUD is fully implemented. Stripe webhook processing is intentionally backend-only; its client-side effect (status lookup on the return page) is wired.

### 5. Reviews, safety, trust & attendance — 70%

The traveler/guest-facing and admin-facing halves of this cluster are implemented to a genuinely high standard end-to-end (real UI + service + wired endpoint), which is unusual for a frontend audit. The frontend service layer under src/app/core/services/ mirrors the backend almost path-for-path: review.service/review.http.ts, safety-report.service.ts, trip-safety.service.ts, no-show.service.ts, admin-review.service.ts, admin-safety.service.ts, admin-trust-safety.service.ts. Public review reading, review creation, my-reviews/about-me, emergency contact, traveler check-in/out, SOS, no-show reporting (logged-in + guest), and the ENTIRE admin moderation surface (hide/unhide reviews, no-show approve/reject/remove-flag, SOS resolve, legacy safety-report triage, trust-safety report status updates, user restrictions create/deactivate) all have concrete UI in confirmation.component, account.component, experience-detail.component and admin.component.

The systematic gap is the HOST-SIDE OPERATIONAL layer of geo attendance. The frontend has zero coverage of the host arrival check-in (slot-level check-in with optional arrival photo), the host attendance roster dashboard, and host marking guests SHOWED/NO_SHOW — no service method, no endpoint string, and nothing in host-dashboard. host-dashboard.component has no safety/check-in/attendance code at all. Guest geofenced check-in only exists on the public confirmation page (guestCheckIn -> POST /public/check-in); the logged-in traveler geofenced arrival variant is folded into the generic trip-safety check-in, and there is no distance/geofence feedback UI beyond a CheckInResult type.

The Booking safety acknowledgement checklist is entirely absent: no service, no endpoint reference, no UI, no i18n keys anywhere in the app.

A few features are inherently backend-only (automatic rating aggregation, enforcement guards, automatic booking completion, check-in data retention purge) — these have no direct UI surface and are scored as N/A-implemented where the frontend correctly consumes their EFFECT (e.g. aggregated rating/reviewCount is displayed), or missing where the frontend cannot observe them. reviewAsHost (host reviews traveler) has a service method (POST /reviews/as-host) but no UI, so host-to-traveler review is only half of the two-way review feature.

- ✗ **Host attendance roster** — none found — no roster/attendance service, DTO, endpoint, or UI; host-dashboard.component.html has no safety/check-in/attendance markup (grep empty).

### 6. Messaging, notifications, comms & engagement — 63%

Strong front-end coverage of the user-facing comms surface. Every area has real HTTP services under src/app/core/services wired to the correct backend routes, plus real UI. Fully done: in-app messaging (thread list, conversation pane, unread badges, mark-read, sender-role 'Admin (Name)' labelling), the in-app notification feed (feed page + header bell, mark-read/mark-all), notification preferences (all 4 toggles in account), the public Contact-Us form, host+platform announcement authoring, the wishlist (add/remove/ids/batch-merge/guest-two-call), and admin conversation monitoring+reply/take-over. The main scoring drag is (1) 5 of the 7 'Notifications' backend features are intentionally backend-internal (outbox worker, dedupe keys, email-provider abstraction, combined email+in-app helper, guest account-less delivery) with no expected front-end surface, so they score 0% for the FE; and (2) several genuine FE gaps below. The FE collapses the backend's ~29 NotificationType catalogue into 5 UI buckets (booking|message|review|moderation|system) in mappers.ts mapNotificationType — all types still surface, just bucketed. Most important true gaps: no 'my waitlist entries / leave' UI and no guest waitlist join UI (WaitlistService.myEntries/leave/joinGuest are defined but unused); no 'hosts I follow' list anywhere (FollowService.myFollows unused by any component); no admin private side-conversation creation UI (ADMIN_CUSTOMER/ADMIN_HOST type exists but no create method); no logged-in segmented newsletter subscribe / own-status check (only public footer subscribe + confirm/unsubscribe landing pages).

### 7. AI, integrations, admin & platform ops — 80%

The admin console is the strongest part of this cluster: features/admin/admin.component.ts wires nearly every backend admin queue and op to a real service+UI (dashboard summary, host-application review approve/reject/request-changes, experience review, review hide/unhide, safety-report triage, no-show/SOS, user status, payment/payout/invoice oversight, city pool, admin ops provisioning). AI itinerary and the host listing-copy assistant both have full UI (trip-planner.component + host-experience-form.draftWithAi) gated on /ai/status. Add-to-calendar is done (Google/Outlook deep-link buttons + a client-built .ics download in confirmation.component). The biggest gaps are entirely absent capabilities rather than half-built ones: (1) Mobile wallet passes — zero code, no Apple/Google wallet service, DTO, or UI anywhere in src. (2) AI moderation classifier, generic WhatsApp click-to-chat, and admin WhatsApp send all exist as service methods but have NO UI invoking them (admin-whatsapp.service.ts even documents 'No dedicated UI yet'). (3) Admin 'create booking on behalf of a user' is missing — admin-bookings.service.ts only lists/gets/cancels/reschedules, no create POST. Rate limiting and several cross-cutting items (health, Swagger, dev bootstrap, async/redis, geo helper) are backend-only concerns with no meaningful client surface; where a client surface exists (error normalization, admin authz via roleGuard, i18n, SEO), it is implemented. Note: the frontend's add-to-calendar .ics is generated client-side rather than fetched from GET /bookings/{id}/calendar.ics, but the deep-links (calendar-links) endpoint IS consumed.
